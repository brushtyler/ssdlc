# Configuration

This page is the reference for authentication, configuration inheritance, model routing, limits, container resources, remote synchronization and toolkit maintenance. For a first setup, the [README](../README.md#basic-configuration) is enough.

## Where configuration comes from

SSDLC reads settings in this order of precedence:

1. the **process environment**;
2. **`<project>/.ssdlc/project.env`**, created by `--init-project` with mode `600`;
3. **`~/.ssdlc/global.env`**, host-wide defaults inherited by every project. Values are loaded without overriding the two sources above.

Configuration is read when the controller starts. Editing `project.env` does not change a controller or container that is already running. Supervised runs freeze their environment at launch and do not reload env files (see [Supervision](supervision.md)).

## Authentication

Log in **once on the host**. With `SSDLC_INHERIT_HOST_*_AUTH="true"`, SSDLC copies the credentials into each project's isolated runtime (`.ssdlc/.runtime/codex_home/`, `.ssdlc/.runtime/claude_home/`). The host stores are never modified.

### OpenAI Codex (ChatGPT Plus / Pro / Team)

```bash
codex auth login     # or run `codex` interactively
```

Credentials are written to `~/.codex/auth.json` (`auth_mode: "chatgpt"`).

### Claude Code (Claude Pro / Max / Team)

- **Persistent login:** `claude auth login`. Open the URL, approve and paste the code. Account metadata goes to `~/.claude.json` and OAuth credentials to `~/.claude/.credentials.json`.
- **Headless token**, for example in CI: `claude setup-token`, then `export CLAUDE_CODE_OAUTH_TOKEN="sk-ant-..."`.

### Antigravity (`agy`)

Docker invocations use a dedicated AGY profile:

- Only the host token at `~/.gemini/antigravity-cli/antigravity-oauth-token` is copied, into `.ssdlc/.runtime/agy_auth/` with permissions `0600`. The AGY container can refresh that copy; the host store is unchanged.
- The AGY profile receives no Claude or Codex credentials and no AI API keys.
- Untrusted verification containers never receive the AGY store.
- If the credentials are missing, the run fails before an interactive login. After you reauthenticate on the host, the next invocation can pick up the newer token.

### API keys

`OPENROUTER_API_KEY`, `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` can be set host-wide in `global.env` or per project in `project.env`, for example for separate billing.

OpenRouter requests are tagged with `HTTP-Referer: https://ssdlc.local/<project-id>` and `X-Title: SSDLC/<project-id>/<ticket-id>`, and their reported usage is recorded in the ticket ledger.

## Model routing

`SquadDispatcher` (also exported as `DynamicRoutingPolicy`) chooses the engine and model for each role. Its inputs are the phase, the risk tier, the development profile from recon (`FRONTEND_UI`, `ALGORITHMIC`, `FULLSTACK`, `REFACTOR`, …) and which providers are available.

A provider counts as available when its credentials are present and its CLI is installed. OpenRouter counts as available when `OPENROUTER_API_KEY` is set.

Default preferences, in order (the first available engine wins):

| Role | Preference |
| --- | --- |
| `00-recon` | agy Gemini Flash → Codex `gpt-6-luna` → OpenRouter Gemini Flash |
| `01-po` | Claude `sonnet` (always first for `FRONTEND_UI`) · agy for Tier S → Claude → OpenRouter |
| `02-design-arch` | Claude `sonnet` → Codex `gpt-6.1-sol` → OpenRouter |
| `02-design-sec` | Codex `gpt-6.1-sol` → OpenRouter DeepSeek-R1 → Claude |
| `03-dev` | Claude for `FRONTEND_UI` · Codex `gpt-6-luna` for Tier S · Claude for `FULLSTACK`/`REFACTOR` · otherwise Codex `gpt-6.1-sol` → Claude → OpenRouter |
| `04-review` | Claude `sonnet` + Codex `gpt-6.1-sol` (cross-model panel) |
| `05-qa` | Claude → agy → OpenRouter |
| `05b-appsec` | OpenRouter DeepSeek-R1 → Codex `gpt-6.1-sol` → Claude |
| `06-ops` | Codex `gpt-6-luna` → agy → Claude → OpenRouter |
| `07-docs` | agy → Codex `gpt-6-luna` → Claude → OpenRouter |

The authoritative source is `SquadDispatcher.dispatch_role` in `orchestrator.py`.

### Per-role overrides

For each role, an explicit engine other than `auto` overrides the dispatcher:

```bash
export SSDLC_RECON_ENGINE="codex";  export SSDLC_RECON_MODEL="gpt-6-luna"
export SSDLC_DEV_ENGINE="claude";   export SSDLC_DEV_MODEL="sonnet"
```

The variable name is built from the **last segment of the phase key**: `SSDLC_RECON_*`, `SSDLC_PO_*`, `SSDLC_ARCH_*` (`02-design-arch`), `SSDLC_SEC_*` (`02-design-sec`), `SSDLC_DEV_*`, `SSDLC_QA_*`, `SSDLC_APPSEC_*`, `SSDLC_OPS_*` and `SSDLC_DOCS_*`.

> [!WARNING]
> The `project.env` template generated by `setup-ssdlc.sh` contains `SSDLC_DESIGN_ARCH_*` and `SSDLC_DESIGN_SEC_*`, but the dispatcher does not read them. Use `SSDLC_ARCH_*` and `SSDLC_SEC_*` to override the design roles.

Review uses a list of models: `SSDLC_REVIEW_MODELS="claude:sonnet,codex:gpt-6.1-sol"`. Entries without an `engine:` prefix use `SSDLC_REVIEW_ENGINE`, which defaults to `openrouter`.

Development options:
- `SSDLC_DEV_USE_OPENROUTER="true"` routes the developer CLI through OpenRouter.
- `SSDLC_DEV_MODEL` sets the model for the Codex role runner.

### Reasoning effort

Base effort for each phase and tier (`BASE_EFFORT_MATRIX`):

| Phase | S | M | L |
| --- | --- | --- | --- |
| `00-recon`, `03-dev`, `05-qa`, `06-ops` | low | low | medium |
| `01-po`, `02-design-*`, `04-review`, `05b-appsec` | low | medium | medium |
| `07-docs` | low | low | low |

How the base effort is adjusted:
- **Retries** raise the effort: one step on attempt 2, two steps from attempt 3.
- **`SSDLC_MAX_REASONING_EFFORT`** (default `medium`) caps every role.
- **Engines** may apply their own limits on top: the Claude CLI accepts only low or medium, and the generated Codex configuration sets its own default. See [#28](https://github.com/brushtyler/ssdlc/issues/28#issuecomment-6796634883).

## Limits and budgets

| Variable | Default | Meaning |
| --- | --- | --- |
| `SSDLC_BUDGET_CAP_USD` | Tier S $3, M $6, L $20 | Reported-spend circuit breaker for the whole ticket (`BUDGET_CAP_GATE`) |
| `SSDLC_DEV_BUDGET_USD` | Tier S $1, M $2.5, L $8 | Per-invocation budget passed to the Claude developer |
| `SSDLC_MAX_DEV_RETRIES` | `3` | Development attempts per task |
| `SSDLC_MAX_DESIGN_ROUNDS` | `5` | Initial limit for a new design session (the template sets `3`) |
| `SSDLC_DEV_TIMEOUT` | `2400` | Developer invocation timeout in seconds |
| `SSDLC_REVIEW_MAX_DIFF_CHARS` | `200000` (max 1,000,000) | Diff input budget for task-mode review and QA |
| `SSDLC_SUPERVISOR_HARD_TIMEOUT` | unset | Optional whole-run deadline for supervised runs |

Recovered and reconciled runs do not use these variables. They use a **frozen limits profile**, with cumulative invocations per role and phase, attempts, dollar caps and an absolute deadline, bound to an explicit authorization. See [Bounded recovery](bounded-recovery.md) and [Historical reconciliation](historical-reconciliation.md).

> [!NOTE]
> Dollar caps count only reported costs: Claude CLI estimates and OpenRouter metered usage. Subscription CLIs such as Codex report tokens but no cost. How these calls are accounted for is tracked in [#43](https://github.com/brushtyler/ssdlc/issues/43).

## Execution mode and containers

- **`SSDLC_EXECUTION_MODE=docker`** (default, recommended). Roles and verification run in containers:
  - verification mounts the source read-only;
  - SSDLC runtime credentials are masked;
  - scratch and cache directories are disposable.
- **`SSDLC_EXECUTION_MODE=local`** isolates caches and removes AI authentication variables, but does not isolate the filesystem. Use it only for trusted code and controlled tests.

Container limits:

| Variable | Default | Notes |
| --- | --- | --- |
| `SSDLC_CONTAINER_MEMORY` | `4g` | |
| `SSDLC_CONTAINER_CPUS` | `2` | |
| `SSDLC_CONTAINER_PIDS_LIMIT` | `1024` (minimum 16) | The generated template sets it twice, and the later value `512` wins |
| `SSDLC_PREFLIGHT_MIN_FREE_MB` | `100` | Minimum free disk space checked by the supervisor preflight |

Role containers use `--init` and a finite PID/thread limit. Before a container exits, a wrapper collects cgroup-v2 PID and memory counters into `.ssdlc/.runtime/resources/ssdlc-role-*.json`. Missing counters are reported as unavailable, never as zero.

When a PID or OOM event is measured, the AI output is blocked and the run raises `ENVIRONMENT_RESOURCE`, preserving the source for reconciliation:
- read-only verification gets at most one retry, in a fresh container;
- developer invocations are never repeated automatically;
- a repeated limit hit exits with code 125.

## Standards and quality contract

- **Standards.** New projects use generic standards. The `yuna` templates require `SSDLC_STANDARDS_PROFILE=yuna` at initialization. Existing project standards are preserved.
- **Quality discovery** recognizes Python tests, Ruff/Mypy configured in `pyproject.toml`, and npm `test`, `lint` and `typecheck` scripts. For other tools, provide `.ssdlc/quality-contract.json` matching `schemas/quality-contract.schema.json`. Required checks must pass on a fresh baseline, and test suites must not be empty.
- **Candidate proof.** Setting `candidate_proof: true` on a required check enables [native gate convergence](native-gate-convergence.md).

## Remote synchronization and GitHub

`SSDLC_SYNC_REMOTE=auto|true|false` (default `auto`) enables synchronization when `origin` is on GitHub or GitLab. `--sync-remote` and `--no-sync-remote` override it for a single `run`, `approve` or `reject`.

Creating issues and pull requests needs an API token. SSDLC reads `GITHUB_TOKEN` or `GH_TOKEN` and does not use the `gh` login automatically:

```bash
gh auth status
export GITHUB_TOKEN="$(gh auth token)"
./ssdlc doctor
```

- **Phase 01-PO:** posts the specification to a new issue, or as a comment on `--issue <number>`.
- **Phase 08-supervisor:**
  - commits the result to `ssdlc/<ticket-id>` and pushes it;
  - on GitHub, opens a **draft PR** that embeds the evidence pack;
  - GitLab gets a branch push only.
- **`approve`:** pushes the merged target branch.

With a token set, the push uses HTTPS and the token, which therefore needs write access to the repository. Without a token, the push uses `origin` and can use an SSH deploy key (see [Troubleshooting](troubleshooting.md#ssh-deploy-keys)). If GitHub returns 403 or 404, check what the token is allowed to do in the repository.

The [feedback workflow](developer-feedback.md#github-projections-and-prerequisite-boundaries) can also publish sanitized, host-owned comments. This is opt-in and part of the frozen profile.

## Maintenance

Shared CLIs are mounted from the toolkit, so updating them applies to every project without rebuilding project containers:

```bash
./setup-ssdlc.sh --update-tools     # or ./ssdlc update-tools from a project
./setup-ssdlc.sh --rebuild-image    # rebuild ssdlc-runner:latest
./setup-ssdlc.sh --versions         # show installed CLI versions
```

`--bootstrap` and `--update-tools` also install the Python requirements into `.tools/python/`. Generated wrappers use that interpreter when it is present.
